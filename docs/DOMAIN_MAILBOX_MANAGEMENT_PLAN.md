# 域名与关联邮箱管理实施计划

- 状态：三个阶段已完成本地实现与自动化验收；尚未部署，真实 Cloudflare Workflow 联调待上线验收。
- 计划日期：2026-10-13。
- 需求来源：[Issue #23：删除域名时提示仍有关联邮箱](https://github.com/mibgb65-cloud/OmniMail/issues/23)。
- 推荐工作分支：`codex/domain-mailbox-management`。
- 实施顺序：统一删除规则与提示 → 关联邮箱列表 → 后台批量清理。

## 1. 目标与成功标准

用户能够在域名管理页直接找到关联邮箱，理解不同操作的影响，并在有权限的情况下批量清理。
移除域名配置和永久清理邮箱必须是两个明确动作，避免用户为了停止使用域名而被迫删除历史邮件。

完成后应满足：

1. 页面提示、API 行为和接口文档一致。
2. 域名旁的邮箱数量可点击，展示关联邮箱、所属用户、主邮箱标记和清理状态。
3. 移除域名配置可以保留邮箱地址、历史邮件、草稿和附件，同时明确停止该域名的新收发与新地址创建。
4. 主管理员可以清理选中的关联邮箱，或清理整个域名的关联邮箱并移除配置。
5. 主邮箱不能被批量操作绕过保护；必须先由所属用户迁移到其他可用邮箱。
6. 页面关闭、重复提交、Workflow 重试和对象存储故障不会导致重复扣减配额或误删其他邮箱。
7. 操作进度可重新查询；部分失败可恢复；后台清理中的邮箱不会被误报为可再次删除。

首版覆盖 Web 管理页面和 Worker API。Android、Float 不新增管理界面，但其既有接口调用保持兼容。

## 3. 方案取舍与首版规则

### 3.1 方案比较

| 方案 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- |
| 只修改提示，引导用户逐个删除 | 改动小 | 仍无法处理其他用户邮箱、主邮箱和清理中的记录 | 仅作为阶段一的临时修正 |
| 前端循环调用个人邮箱删除接口 | 表面实现快 | 受当前用户权限限制；页面关闭中断；缺少整体进度与重试 | 不采用 |
| 区分移除配置与清理数据，提供服务端批量任务 | 影响明确；可兼容旧接口；可恢复 | 需要增加列表与任务记录 | 推荐 |

### 3.2 操作语义

| 操作 | 邮箱及历史数据 | 新邮箱创建与新收发 | 邀请 | Cloudflare 配置 |
| --- | --- | --- | --- | --- |
| 停用域名 | 保留，可读取历史数据 | 停止 | 使用该域名的新注册不可继续 | 不修改 |
| 移除域名配置 | 保留，可读取历史数据 | 停止 | 相关邀请失效 | 不修改 |
| 清理选中的邮箱 | 永久清理选中地址的主存储数据 | 选中地址停止使用；其他地址按原域名状态工作 | 仍保留，后续可再次分配释放的地址 | 不修改 |
| 清理全部关联邮箱并移除配置 | 永久清理全部目标地址的主存储数据 | 整个域名停止使用 | 相关邀请失效 | 不修改 |

补充规则：

- 永久清理包含目标邮箱的历史邮件、草稿、附件、原始邮件和翻译缓存；备份仍按既有保留策略保存。
- 移除配置后保留的草稿可读取，但原地址的发送和保存行为需与当前“域名不可用”规则保持一致并明确提示。
- 停用域名不承诺撤销已经进入外部发信服务的邮件；界面说明停止的是后续新操作。
- 重新添加同名域名后，仍启用的保留邮箱可以恢复使用；重新添加前必须提示这一影响。
- “移除配置”是网页的常规删除动作；永久清理放在明确标识的危险操作区域。
- 存在活动清理任务时，不允许移除、重新启用或重新添加同名域名，避免旧任务作用于新配置。
- 全域清理遇到任一主邮箱时，整体拒绝启动并列出阻塞项，不能静默跳过后仍宣称域名已清空。
- 选中清理仅处理明确选定且可删除的邮箱，不能静默扩大到其他记录。

### 3.3 权限与数据范围

| 能力 | 管理员 | 主管理员 | 普通用户与临时用户 |
| --- | --- | --- | --- |
| 查看域名关联邮箱和必要的所属用户信息 | 允许，沿用现有管理数据权限 | 允许 | 禁止 |
| 停用域名、移除配置并保留历史数据 | 允许 | 允许 | 禁止 |
| 新的管理页批量清理接口、任务详情和重试 | 禁止 | 允许 | 禁止 |
| 个人邮箱删除接口 | 保持现有规则，只能处理本人邮箱 | 保持现有规则，只能处理本人邮箱 | 保持现有权限规则 |

首版不代替其他用户迁移主邮箱，不删除用户账号，不操作外部 Provider 账号和远端邮件。

无人收件存储在共享系统邮箱 `__unassigned__@omnimail.invalid` 中，不属于某个域名的关联邮箱。
首版批量清理不删除系统邮箱，也不清理其中按 `delivered_to` 记录的该域名历史邮件。
全域清理预览需单独提示这类历史数据的保留范围，避免“关联邮箱已清理”被理解为“该域名所有历史邮件已删除”。

## 4. 页面流程

### 4.1 域名列表与关联邮箱

- 域名行展示总关联数，并区分可见邮箱、主邮箱和清理中的邮箱，避免仅靠一个总数解释删除失败。
- 点击数量或“查看关联邮箱”打开列表面板，提供地址、所属用户、启用状态、主邮箱标记和清理状态。
- 服务端分页；默认每页 50 条，上限 100 条。这是应用设计上限，不是 Cloudflare 平台限制。
- 主邮箱不可选，提供“请所属用户先设置其他主邮箱”的说明；清理中的记录不可再次提交。
- 支持当前页多选；“清理全部关联邮箱”使用独立入口，不能把当前页全选误当成全部数据。
- 列表失败显示重试入口；任务提交后刷新域名统计和邮箱状态。

### 4.2 移除配置

1. 展示域名、保留的关联邮箱数量、停止新收发与创建、邀请失效等影响。
2. 按钮使用“移除域名配置”，避免与永久清理共用“删除”这一含糊标签。
3. 成功后移除管理列表中的配置项，并刷新当前页面依赖的数据。
4. 邮件工作区保留历史访问入口；邮箱状态明确显示域名未配置，不能仍提示“正在接收邮件”。

### 4.3 永久清理

1. 服务端预览目标范围，展示涉及用户、邮箱、邮件、草稿、附件、主存储字节数和阻塞项。
2. 输入完整域名确认，并明确历史数据永久删除、备份按保留策略保存。
3. 提交成功显示“清理任务已提交”，而不是“已全部删除”。
4. 展示已完成、待处理、失败和待对象清理数量；关闭面板后可从域名管理入口重新打开任务。
5. 只有所有目标及其对象清理完成，才展示“清理完成”；全域模式随后移除域名配置。
6. 任务失败展示已完成范围和可重试项；清理开始后不提供会暗示恢复数据的“撤销”按钮。

复用 `DangerConfirmDialog`。其当前确认框固定使用数字输入模式，焦点循环也仅包含按钮；
新增域名输入确认时，需要支持文本输入，并将输入框纳入焦点循环，验证 Tab、Shift+Tab、Escape 和关闭后焦点恢复。

## 5. API 设计草案与兼容策略

以下协议已接入 API client、类型、API 目录与生成文档；以 [API 参考](api/admin-access.md) 和 [使用及部署说明](DOMAIN_MAILBOX_MANAGEMENT.md) 为准。

| 接口 | 行为 | 权限与响应 |
| --- | --- | --- |
| `DELETE /api/admin/domains/:name` | 保留旧行为，仅删除空域名 | 管理员；保持 `200 { ok: true }` 和非空域名 `409` |
| `DELETE /api/admin/domains/:name?mode=configuration` | 显式移除配置，保留邮箱和历史数据 | 管理员；`200 { ok: true }` |
| `GET /api/admin/domains/:name/mailboxes` | 分页读取关联邮箱，含隐藏清理记录 | 管理员；`200` |
| `POST /api/admin/domains/:name/cleanup/preview` | 预估 `selected` 或 `all_and_remove` 范围 | 主管理员；`200`，返回短期有效的预览标识 |
| `POST /api/admin/domains/:name/cleanup` | 校验预览与确认信息，持久化并提交任务 | 主管理员；`202 { jobId, status }` |
| `GET /api/admin/domain-cleanup-jobs/:id` | 返回汇总进度、待处理对象数量与任务级错误 | 主管理员；`200` |
| `POST /api/admin/domain-cleanup-jobs/:id/retry` | 恢复同一任务未完成部分 | 主管理员；`202` |

协议约束：

- 域名沿用现有规范化和长度校验；未知 `mode`、非法 URI 编码和非法请求体返回 `400`。
- `selected` 接收去重后的地址数组，首版每次最多 100 个；逐个校验格式、长度、精确域名和所属用户。
- `all_and_remove` 由服务端确定全部目标，不信任客户端传来的目标总数或地址列表。
- 必须使用精确域名比较，`example.com` 不匹配 `sub.example.com` 或 `notexample.com`。
- 预览标识绑定操作者、域名、模式和目标集合，并有有效期；客户端数量不能充当唯一授权依据。
- 提交重新校验目标集合、主邮箱、已有任务和权限。关键范围变化返回 `409` 并要求重新预览；
  期间新邮件导致的数量变化可更新预览，但不能默默扩大已确认的目标邮箱集合。
- 幂等键绑定操作者及请求内容；相同请求返回已有任务，不重复创建 Workflow。
- 任务参数由服务端生成，客户端不得传入用户 ID、R2 key、SQL、Workflow 实例 ID 或任意清理条件。
- 分页、错误和响应复用仓库现有约定；任务失败详情不得包含邮件正文、凭据或原始外部错误。

## 6. 后台清理与数据一致性

### 6.1 最小必要持久化

批量清理阶段新增一份 D1 迁移，序号以实施时最新迁移为准，同时更新运行时 schema 和迁移测试。

建议增加：

- `domain_cleanup_jobs`：任务 ID、域名、模式、操作者、幂等键、状态、冻结前状态、进度及错误摘要。
- `domain_cleanup_items`：任务与邮箱的关联、邮箱地址、原所属用户、原启用状态、处理状态和错误码。
- 邮箱清理归属标记：使执行器能够确认当前记录仍属于本次清理；不能仅凭邮箱地址重复扫描。
- 待删除对象与任务的关联：复用 `pending_object_deletions`，能够判定本任务是否还有未删除的 R2 对象。

活动任务对同一域名互斥；任务记录不能因为移除域名而级联删除。
任务状态至少覆盖 `pending`、`running`、`waiting_for_objects`、`failed`、`completed`。
失败保留已完成进度，重试沿用同一目标集合；不能通过重新预览扩大旧任务。

### 6.2 提交与执行顺序

1. **校验并冻结。** 在数据库条件写入中重新检查主邮箱和活动任务，持久化任务与目标快照，
   标记目标邮箱不可收发；全域模式同时冻结域名并使相关邀请不可使用。
2. **可靠派发。** 提交意图先存入 D1，再创建可确定身份的 Workflow；派发失败或响应丢失时，
   状态查询、重试和现有调度入口能够恢复派发，不留下无任务接管的隐藏邮箱。
3. **分批清理。** 扩展现有 `CLEANUP_WORKFLOW` 编排；复用邮件、草稿和对象删除服务，
   将进度持久化，不把全部对象键或全部邮箱传入一次 Workflow 参数。
4. **确认归属。** 每一批删除前确认任务、邮箱标记和所属用户仍匹配；归属变化停止该项，
   不能沿用旧地址继续删除。与主管理员身份同步及账号清理交叉执行的场景需单独验证。
5. **记录结果。** 数据库中的配额变化、对象删除待办和记录删除按既有机制完成；
   清理中的 R2 对象持续计入任务待办，不能把对象删除异常吞掉后标记成功。
6. **最终收尾。** 等目标记录和对象待办全部清理完成，写入完成审计；
   全域模式再次确认域名未产生新关联、配置仍受该任务控制，再处理邀请并移除配置。

D1 的 `batch()` 可在数据库内将一组 SQL 作为事务执行，但不能覆盖 Workflow 创建和 R2 删除。
跨服务一致性由持久化派发意图、目标归属检查及可重复执行的补偿流程保证。
依据：[D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/)。

Workflow 的外部读写应放入步骤中，按可重试执行设计；步骤重试不能重复扣减配额或重复扩展清理范围。
依据：[Rules of Workflows](https://developers.cloudflare.com/workflows/build/rules-of-workflows/)、
[Trigger Workflows](https://developers.cloudflare.com/workflows/build/trigger-workflows/)。

### 6.3 并发和失败规则

- 不能仅先查询再删除；必须通过条件 SQL、任务归属和唯一约束保护提交与最终移除。
- 创建、启用、主邮箱切换和邀请注册等写入口必须检查活动清理标记，数据库写入时也要保持该条件。
- 已在队列中的收件解析、发送和通知需要检查目标是否仍可用，避免隐藏或删除后重新写入数据。
- 全域清理接管前已隐藏的个人删除记录时，应识别原任务并等待或安全接管；不能启动两份并行清理。
- 首个永久删除发生前，可在确认没有执行器接管的情况下恢复启动失败的冻结状态；
  开始永久删除后保留冻结并重试，不能提示数据已恢复。
- 全域清理失败时域名保持冻结且配置尚未移除；选中清理失败时其他邮箱继续按原状态工作。
- 清理完成前禁止释放地址供重新分配；完成后旧任务重试必须被完成状态和归属标记拦截。
- 主邮箱保护、账号权限、现有个人删除与保留策略清理必须保持有效。

## 7. 分阶段实施清单

### 阶段一：统一删除规则与提示

- [ ] 为配置移除增加显式 `mode=configuration`，保留无参数接口旧行为。
- [ ] 同一数据库批次处理邀请和域名配置，新增准确的审计详情。
- [ ] 网页常规移除调用显式模式，确认弹窗与后端行为一致。
- [ ] 保留邮箱的工作区状态正确显示域名不可用；历史邮件、草稿、附件可读取。
- [ ] 同步英文文案、API 目录和生成文档。

### 9.1 最小充分验证

| 验证层 | 必须覆盖的场景 |

### 9.2 发布与回滚

- 阶段一、二可独立合入；阶段三迁移先就绪，再开放批量操作入口。
- 复用现有 `CLEANUP_WORKFLOW` 绑定，实施时核对当前 Workflows 限制和项目运行配置；
  本计划不预设需要新增 Cloudflare 服务或修改生产配置。
- 阶段三的 schema 更新同时覆盖 CLI 迁移与运行时初始化，验证空库和已有数据库升级。
- 发布说明写清停用域名实际影响、显式移除配置协议、永久清理范围以及备份保留规则。
- 回滚先关闭新任务提交；已有任务需由兼容版本继续运行或完成恢复处理。
  存在活动任务时不能直接回滚到不理解新任务参数的旧 Worker。
- 新表优先保留，避免回滚删除任务进度；配置重新添加不能恢复已经永久清理的数据。

## 10. 实施前重点核对与后续范围

以下是实现时需要验证的技术点，不要求在本计划阶段额外确认：

1. 主管理员身份同步目前可能调整隐藏邮箱归属，需要与清理目标归属检查配合，防止清理失效或误删。
2. 原个人删除任务缺少管理页任务状态，接入关联列表时应补足“正在清理”和“启动失败”的解释。
3. 对象删除服务目前允许暂时失败后补偿；批量任务必须能准确关联待办，不能只靠邮箱记录是否消失判断完成。
4. 原有收发队列、草稿保存和主邮箱切换的并发行为，必须以真实 D1/R2 测试确认冻结边界。

后续需求单独评估：普通管理员跨用户永久清理授权、代用户迁移主邮箱、无人收件按域名清理、
导出后删除、Android/Float 管理界面，以及实例级统一后台任务中心。
这些功能不作为本次首版完成条件。
