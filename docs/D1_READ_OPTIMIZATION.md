# 邮件列表 D1 读取优化

本次针对线上占用最多读取额度的按邮箱筛选列表和数量统计，保留 HTTP 请求及响应契约。

## 变更

- 迁移 `0036_message_read_optimization.sql` 新增一个以实际收件地址
  `COALESCE(delivered_to, mailbox_address)` 开头的复合索引，后续包含文件夹和分页排序字段。
  普通邮件与未分配邮件使用原有地址语义；用户归属和隐藏邮箱限制仍由原查询检查。
- 数量统计在 Worker 实例内按 D1 绑定、用户、角色、邮箱范围与数据版本复用；缓存最多
  256 个范围，每项有效期 60 秒，访问不续期。失效或新实例会重新查询，不写 D1 缓存表。
- 翻页、切换文件夹和搜索可以复用同一邮箱范围的数量；读取邮件列表的同一数据库批次
  会核对版本，若缓存版本已过期，则重新读取列表、统计和版本，避免并发操作导致不一致。
- 邮箱隐藏、归属和地址变化会使相关用户的版本失效。草稿新增/删除沿用现有失效触发器。
- 消息同步触发器仅在字段实际变化时更新版本。重复已读、星标操作通过 SQL 条件跳过
  空更新，减少索引维护及版本更新的写入量。真实状态变化仍立即反映到下一次读取。

新索引未包含频繁改变的已读和星标值，但新增邮件及改变收件地址、文件夹、排序仍会维护
该索引。此取舍应同时观察 `rows_read` 和 `rows_written`，不能只看接口耗时。

## 升级与验证

使用 `npm run deploy`，让部署脚本先完成数据库迁移，再上传 Worker。旧数据库的恢复入口
也识别 0036；不需要新增资源绑定或 Secret。索引首次创建需要扫描已有邮件并写入索引，
应在额度恢复或有足够余量后执行。代码部署不能重置已耗尽的免费日额度。

验证命令：

```bash
npm run check
npm test -- message-list-api.test.ts message-count-cache.test.ts message-bulk-api.test.ts schema.test.ts apply-d1-migrations.test.ts bootstrap-legacy-d1.test.ts
npm run test:worker -- email-worker/integration/message-read-optimization.integration.ts
```

集成测试在本地 D1 的同一份 1,282 封模拟邮件上比较迁移前后读取行数，并验证分页不重不漏、
统计复用、零缓存写入、并发一致性、跨用户/角色隔离、未分配邮件、邮箱可见性及草稿变化。
测试要求冷读取行数减少超过 50%；这只是该样本的结果，不代表所有真实查询的固定降幅。

本次本地 D1 实测，列表与统计批次读取行数从 2,252 降至 224，约减少 90%；复用统计后的
第二页批次读取 93 行。这些数字不包括请求前的单行版本检查，三个批次均未写入业务数据。
测试的 `benchmark` 注解保留每次运行的对比数据。

缓存不跨 Worker 实例共享。实例重启、冷启动或流量被分散到不同实例时会重新统计，索引
仍然有效。全用户、按域名或任意正文搜索的首次聚合仍可能扫描较多邮件，需要根据上线后的
D1 Insights 再决定是否增加针对性方案。

参考：[Cloudflare D1 索引与读取成本](https://developers.cloudflare.com/d1/best-practices/use-indexes/)。

## 外部同步、搜索与通知的进一步优化

新增迁移 `0037_mail_notification_versions.sql`，为外部邮箱通知维护按用户和来源划分的
版本。主管理员的密钥迁移仍只由页面主动发起，与这里的邮件同步和搜索补全无关。

1. Gmail、QQ、NAVER、Yandex、Microsoft、iCloud、Linux DO 的消息索引 Upsert 增加实际
   字段比较。相同内容不会只为刷新 `updated_at` 而重写。Flags/Labels 去重排序；远端缺失
   日期时，更新保留旧日期。远端已读状态仍按原同步流程核对。
2. 索引裁剪在新增邮件、UIDValidity 变化、保留上限变化时执行；同一实例首次处理及每六小时
   也重新核查一次。成功后才记忆状态，失败重试不会漏清理。记忆只驻留实例内，不写数据库。
3. 历史搜索补全每轮最多扫描 200 封、投递 20 个任务，保存最后检查的邮件 ID；整个扫描
   完成后等待一天再核查。新邮件仍在解析批次中写入搜索索引。队列发送失败不推进游标，
   重复索引任务遇到相同内容不会重写；最终失败记录由低频核查再次发现。
4. 通知先按来源读取有限候选，再合并；准确未读总数单独统计，不受返回条数限制。缓存最多
   128 个查询，每份结果最大 256 KiB，最长五分钟，每次请求先校验来源版本。
   不把同步时间戳计入通知版本；实际消息变更、账号归属变化及删除才失效。冷请求仍需计算
   总数，缓存不跨实例共享，不能把缓存命中等同于完全不查询 D1。
5. Worker 对明确 D1 免费日读写额度错误执行 30 秒至五分钟退避，返回 `503`、
   `code=d1_daily_limit`、`resetAt` 和 `Retry-After`。Web 与扩展据此暂停短期重复请求，
   Web 使用用户本地时区显示恢复提示。探测成功后自动恢复，实例重启会重新探测。
   定时任务遇到额度错误结束本轮；队列延后至次日额度周期重试，遵循现有重试次数及死信策略。
   已被发信服务接受的邮件仍沿用原确认逻辑，避免重复投递；收信失败继续报错，不伪装成功。

通知版本触发器在真实变更时增加少量写入；无变化同步的消息写入为零，包含通知版本也不写。
上线后同时检查读写指标。需先应用 0036/0037 再更新应用；执行 `npm run deploy` 会按顺序
处理迁移。部署和重试不会重置免费额度，旧版回滚后的通知缓存一致性不作保证。

回归测试覆盖七种邮箱的重复写入、连续同步裁剪条件、补全失败恢复、准确未读总数、用户隔离、
账号转移及级联删除、HTTP 错误提示、数据库退避和队列延迟重试。真实邮箱同步和线上消耗变化
仍需部署后观察；本地测试不会发送真实邮件或修改线上账号。
